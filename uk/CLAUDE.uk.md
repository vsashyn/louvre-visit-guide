# Путівник по Лувру

Переклад `CLAUDE.md`. Англійський оригінал у корені репозиторію лишається чинним документом для
інструментів. Цей файл існує для читання людиною і навмисно названий `CLAUDE.uk.md`, щоб Claude Code
не підхоплював його як інструкції.

---

Мобільний путівник для відвідин Лувру. Відвідувач обирає твір і отримує його історію текстом,
зображеннями та аудіо.

## Що застосунок мусить робити

- Повністю працювати офлайн. Музейний вайфай і мобільний зв'язок у залах ненадійні, тож усе потрібне
  завантажується до візиту й читається з локального сховища. Жоден мережевий запит не допускається на
  критичному шляху перегляду експоната.
- Нести три типи медіа на кожен експонат. Текст, зображення твору й начитану аудіодоріжку, яку
  відвідувач слухає, стоячи перед твором.
- Давати змогу обрати експонат і заглибитися в нього. Вибір може йти з перегляду списку, пошуку або
  обходу зали, і він відкриває повну розповідь, а не підпис.
- Підходити для користування однією рукою в переповненій залі. Короткі сеанси читання, великі зони
  дотику, аудіо, яке грає з телефоном у кишені.

## Структура репозиторію

- `assets/` містить вміст, по одному файлу Markdown на експонат. Наявні 78 файлів, які охоплюють усі
  три крила: живопис, скульптуру, предмети та зали. `assets/INDEX.md` це згенерована таблиця всіх
  них, згрупована за крилом і рівнем.
- `docs/technical-design.md` це план реалізації. Прочитайте його перед тим, як писати код застосунку.
- `docs/archive/` містить застарілі плани. Тільки для довідки, не будуйте за ними.
- `.claude/` містить налаштування Claude Code.
- `uk/` містить український переклад усього вмісту.

## Стек

Офлайн-перший вебзастосунок, зібраний на Vite і ванільному JavaScript, розміщений як статичний сайт
на Cloudflare і встановлений на домашній екран iPhone, де працює автономно. Без фреймворку, без
вебшрифтів, без сторонніх запитів під час роботи. Ранній план нативного iOS відкинуто, див.
`docs/archive/native-ios-plan.md`.

`assets/` є джерелом істини. Скрипт Python на Mac перетворює його на `content.json`, по одній
доріжці AAC на твір і зображення WebP. Застосунок ніколи не парсить Markdown під час роботи.

Офлайн це жорстка вимога, а не функція. Написаний вручну service worker віддає все з кешу без
мережевого запасного варіанта, медіа завантажується через явну кнопку в застосунку, а не ліниво, і
аудіо відтворюється з blob-URL, прочитаних із Cache API, а не через service worker, бо Safari
потребує відповідей 206 на запити Range. Тримайте весь обсяг близько 25 МБ, щоб квота сховища ніколи
не стала проєктним обмеженням. `docs/technical-design.md` містить обґрунтування й решту тактик.

Коду застосунку поки не існує.

## Формат вмісту

Кожен файл у `assets/` це Markdown із заголовком YAML. Ім'я файлу збігається з `id`.

Поля заголовка: `id`, `title`, `title_fr`, `artist`, `artist_dates`, `date`, `medium`, `dimensions`,
`inventory`, `department`, `wing`, `level`, `room`, `gallery`, `category`, `tags`, `time_needed`,
`crowd`, `image`, `image_source`, `image_license`.

Розділи тіла, у цьому порядку:

1. `# Назва`, далі рядок із розташуванням: автор, дата, крило, рівень і зала.
2. `## In one line`
3. `## What you are looking at`
4. `## The story`
5. `## Look for`
6. `## Interesting facts`
7. `## Practical`, лише коли залу треба супроводити порадою про черги чи час.
8. `## Talking point`

Тримайтеся цієї форми в нових файлах. Розділи відповідають екранам застосунку й сегментам аудіо, тож
перейменування чи перестановка ламає подальшу роботу.

## Як писати вміст

Голос задають наявні файли. Дотримуйтеся його.

- Конкретні факти з іменами, датами й місцями. «Нотатка флорентійського урядовця Аґостіно Веспуччі в
  жовтні 1503 року», а не «дослідники вважають».
- Пишіть для людини, яка стоїть у залі, втомлена й оточена натовпом. Кажіть їй, куди дивитися.
- Жодного мистецтвознавчого жаргону без негайного простого пояснення.
- Пункти `Look for` це фізичні речі, видимі на поверхні, а не тлумачення.
- Зали, інвентарні номери й дати мусять бути перевірними. Позначайте непевне, а не згладжуйте його.
